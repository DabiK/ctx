  symlinks component-wise, `isDirectory` follows links, and `readDir` surfaces

## 2026-08-20 — #5 Git context operations

- Added read-only Git context operations through the same boundary and protocol:
  direct `status`, `changed [path]`, `diff [--staged] [path]`, `log [path]`
  (bounded by default), and `show <rev> <path>` commands plus the corresponding
  `@ctx` ops.
- `GitPort` is the fixed allowlist of Git behavior: `status`, `diff`, `log`, and
  `show`, each mapping to one well-defined read-only `git` invocation with a
  static argument list (no shell, no arbitrary Git execution). Values from the
  application layer (validated paths, safe revisions, limits) are passed as
  separate argv elements.
- `SystemGit` gained the four operations with pure, exported parsers
  (`parsePorcelainV1` buckets staged/modified/untracked/deleted and parses the
  branch line incl. detached HEAD and unborn branches; `parseNumstat` sums
  insertions/deletions; `parseLogOutput` parses `%h|%ad|%s`). Diff runs
  `--numstat` (summary) and the full text in parallel; scoped paths use the
  `:(literal)` pathspec so glob/magic characters match as themselves; an empty
  (unborn) repository is an empty log state, not a failure.
- `GitUseCase` (application layer) applies the boundary uniformly: scoped paths
  for changed/diff/log are validated with `PathGuard.guardDir` and refusals are
  explained parts, never silent filters; `show` validates its revision and path
  syntactically (`isSafeRevision`/`isSafeShowPath` in `protocol.ts`) and reads
  only from the object store, so it can show files deleted from the working
  tree. Unsafe revisions/command fragments are refused at parse time (whole
  request), CLI parse time, and defensively in the use case before the port.
- Protocol parser gained `status`, `changed [path]`, `diff [--staged] [path]`,
  `log [--limit N] [path]`, and `show <rev> <path>`; `SUPPORTED_OPS` updated;
  mixed Git/read/discovery requests produce one combined `# CTX RESPONSE`.
- CLI gained the five commands with `--staged` and `--limit` wiring, per-command
  help, and usage errors for malformed/unsafe show forms.
- Response builders: `buildStatusPart` (branch + per-state counts and lists),
  `buildChangedPart` (flat list with state), `buildDiffPart` (summary numbers +
  diff text), `buildLogPart` (explicit `limited: yes (max N)` when the bound is
  hit), `buildShowPart` (content or the Git diagnostic).
- Tests: unit suites for the protocol parser (git ops, safe-rev/path allowlist),
  the GitUseCase with fake Git/Fs ports, the pure platform parsers, and the CLI;
  real-temporary-repository integration coverage for normal results, staged vs
  working-tree diffs, path scoping, empty states (clean tree, no commits, empty
  diff), bad revisions, deleted-file `show`, protocol round trips, unsafe-rev
  refusal, and non-repository failure. 198 tests pass; typecheck clean.
- Verified the packaged CLI manually on macOS: status/changed/diff (working +
  staged + scoped)/log/show, a combined `@ctx status + @ctx log + @ctx show`
  round trip, unsafe `@ctx show a..b` refusal copied to the clipboard, and
  non-repository failure with an actionable message.

## 2026-08-20 — #6 Batch, budgets and recovery

- Added `@ctx batch` as an explicit multi-operation container: one `@ctx batch`
  line followed by one `@ctx` operation per line (in declared order). The parser
  flattens the members into the existing ordered execution; a batch must contain
  at least one operation, accepts no arguments, and refuses nested `@ctx batch`
  (`malformed nesting`) and empty batches up front. `ParsedRequest` carries a
  `batch` flag; batch requests always render the batch envelope, while plain
  read-only multi-line requests keep the legacy byte-identical single read
  response.
- Budget limits from `.ctx.toml`: `max_file_bytes` (default 256 KiB, hard cap
  16 MiB) and `max_batch_bytes` (default 1 MiB, hard cap 128 MiB), with
  `clampFileBytes`/`clampBatchBytes`; the `.ctx.toml` template documents them.
- Per-file budget: a read whose rendered selected content would exceed
  `max_file_bytes` is omitted with an explicit explanation (`content exceeds the
  per-file budget … request a smaller range or raise max_file_bytes`) — never
  silently truncated — in direct reads, batch members, and combined requests.
- Total-output budget: before any copied response, its byte size is measured;
  when it would exceed `max_batch_bytes` the full content is not copied. Instead
  a structured `## Response too large — reduce scope` recovery response is
  copied, listing the most expensive requested sections by bytes and asking the
  LLM to reduce scope. Applied to single-op `--copy` commands (via
  `finishDiscoveryOp`, which now reads each operation's clamped budget from
  `OpExecution.maxBatchBytes`), to `ctx files`/read-only requests (via
  `readSpecs`), and to combined/batch requests (via `executeCombined`).
- Batch responses carry a `## Batch response` summary with total bytes/tokens
  and the configured limits (`Operations: N | bytes: B | tokens: ~T` and
  `limits: total ≤ … | per-file ≤ …`); per-part byte/token metadata and
  `limited: yes (max N)` notices were already in place.
- Protocol prompt and `read` CLI help document the batch syntax and the
  fail-closed budget behavior.
- Tests: protocol parser (batch members/order, nesting/empty/arg refusals,
  non-batch flag), config (budget keys, defaults, hard-cap clamping), read
  (per-file omission + total-budget recovery incl. smaller-range success), request
  (batch envelope/order, file-only batch, batch total-budget recovery, batch
  per-file omission), CLI (batch round trip), and real-temporary-repository
  integration (ordered batch and fail-closed recovery). 216 tests pass;
  typecheck clean. Verified the packaged CLI manually on macOS: ordered batch
  round trip, per-file omission with explanation, total-budget recovery
  (combined and single-op `--copy`), and batch nesting/empty/argument refusals.

## 2026-08-20 — #7 Controlled writes and sequences

- Added the first controlled repository modification from tagged LLM proposals:
  `@ctx patch` (one multi-file unified diff body), `@ctx write <path>` (a
  fenced or raw full-file body), and `@ctx sequence` (one write proposal
  followed by verification reads that run only after the write). `ctx read`
  validates and preflights a proposal and copies a preview — nothing changes;
  the new explicit `ctx apply` command is the approval that applies it.
- Protocol parser: proposal bodies span multiple lines until the next `@ctx`
  line; ```/~~~ fenced bodies close before it (language tags dropped, content
  after the closing fence refused, unterminated fences refused); @ctx-looking
  lines inside an open fence stay content; leading whitespace before `@ctx`
  stays tolerated. A proposal must be the only operation of the request (or a
  sequence's first member); proposals are refused inside `batch`, as are
  mixed read+proposal requests, sequences that do not start with a write,
  sequences without verification reads, and sequences with two writes. Pure
  helpers: `splitFencedBody`, `extractDiffTargets` (a/ b/ prefixes stripped,
  change kinds new/deleted/renamed/modified, dedupe), `isSafeWritePath`.
- Write boundary: `PathGuard.guardWrite` validates write targets
  repository-relative, inside the repository ROOT only (configured
  allowed_roots stay read-only), honours `.ctxignore` and sensitive-path rules,
  refuses the `.ctx.toml`/`.ctxignore` permission-boundary files, refuses
  existing directory targets, and resolves the deepest existing ancestor so
  symlink escapes and broken links fail closed. Sensitive write content is
  refused without an explicit override: full bodies via
  `containsSensitiveContent`, patches via the new `diffAddsSensitiveContent`
  (added lines only, so key-removal cleanup diffs pass).
- Ports/adapters: `GitPort` gained `checkPatch` (`git apply --check`) and
  `applyPatch` (`git apply`, Git as the recovery path), implemented in
  `SystemGit` by feeding the patch through stdin (`spawn`, never written to
  disk); `FsPort` gained `mkdirs` (SystemFs recursive mkdir) for creating
  missing parent directories of accepted full writes. The CLI adapter wires the
  new `apply` command (no args, `--allow-sensitive`).
- `WriteUseCase` (application layer): validates proposals, preflights patches
  before any change, applies patch/write, and runs sequence verification reads
  only after the write succeeds (skipped with an explicit reason when the write
  is refused or fails). Copied responses are structured `# CTX RESPONSE`
  blocks: `## Patch proposal — ready to apply` / `## Patch applied` /
  `## Sequence — write applied` with verification sections, or `## … refused`
  with per-target reasons, preflight/apply diagnostics, and `No files
  changed.`; an oversized verification response fails closed with an applied
  note instead of silently truncating.
- Shared operation execution extracted into `OpCollector`
  (`src/application/collect.ts`) so combined requests, batches, and sequence
  verification reads render identical sections through the same boundary.
- Protocol prompt (full + compact) now says `ctx read` validates/preflights
  proposals and `ctx apply` is the approval step.
- Tests: protocol parsing (proposal bodies, fences, mixing/nesting refusals,
  diff targets), `guardWrite` boundary suite, `WriteUseCase` unit tests with
  fakes (preview without change, sensitive/ignored/boundary refusals,
  apply success/failure, sequence conditional behavior, apply-with-no-proposal),
  CLI `apply` command, and real-temporary-Git-repository integration (multi-file
  patch preview/apply, patch failure, new-file patches via `git add -N`, full
  writes with parent dirs, sensitive-write refusal, sequence verification
  order, non-repository failure). 275 tests pass; typecheck clean. Verified the
  packaged CLI manually on macOS: patch preview (no change), `ctx apply`,
  full-write preview/apply, sequence apply with verification reads, and
  sensitive/traversal refusals.

## 2026-08-20 — #8 Watcher TUI: safe and auto

- Added the foreground `ctx watch` mini-TUI in safe and auto modes through the
  same hexagonal boundary. The new `WatchUseCase` (`src/application/watch.ts`)
  is the application logic: a loop that polls the clipboard on a clock tick,
  handles keys, and renders through the TUI port.
- New application ports (`src/application/ports.ts`): `ClockPort` (deterministic
  `now()` and `pollIntervalMs()` for tick cadence and event timestamps) and
  `TuiPort` (`open`/`render`/`nextKey`/`readLine`/`confirm`/`showDetail`/`close`)
  with the shared `WatchMode`, `WatchEvent`, `PendingWrite`, and `WatcherView`
  contracts. Infrastructure adapters: `SystemClock` (`src/platform/clock.ts`)
  and `SystemTui` (`src/platform/tui.ts`, raw-mode keyboard input + ANSI frames,
  no external dependencies). Both are wired into `PlatformPorts`/`main` and the
  new `ctx watch` CLI command (`--allow-sensitive`, help, parse rules).
- Loop prevention: `fnv1a` (pure FNV-1a hash in `common.ts`) detects duplicate
  clipboard content; content starting with `# CTX RESPONSE` is logged as an
  ignored own response. Malformed requests get a structured refusal copied
  (never executed), matching `ctx read` behavior.
- Read requests: safe mode confirms each request (`y/n`); auto mode runs valid
  reads automatically. Both execute through the shared `RequestUseCase.execute`
  path and copy the identical response the CLI produces.
- Write proposals (`@ctx patch`/`write`/`sequence`): surfaced as pending writes
  in the TUI with label, targets, status note, and full preview text — the
  proposal stays untouched in the clipboard. `p` previews (full-screen detail),
  `c` cancels, and `a` applies through the explicit action only (in both modes;
  safe mode additionally confirms detection and application). Applying runs
  through the shared `WriteUseCase.applyParsed` path, so sequence verification
  reads still run only after the write succeeds.
- Command entry (`e`): executes supported read operations via a new pure
  `parseCommandOp` in `protocol.ts` (same parser as the protocol read ops) and
  automatically copies their structured response.
- Refactors for reuse without a god service: `RequestUseCase` gained a public
  `execute(parsed, opts)` that runs a parsed request end-to-end (config,
  budgets, legacy/combined/batch envelopes, fail-closed recovery) and returns
  the copied response plus report lines the caller surfaces on its own channel
  (terminal for `ctx read`, TUI events for the watcher); `WriteUseCase` gained
  `previewParsed` (validate + build preview/refusal text without copying) and
  `applyParsed` (validate + apply + verify + copy), used by both the CLI
  `apply`/`read` commands and the watcher. `Proposal`, `ParsedOkRequest`,
  `isProposalRequest`, `singleProposal`, and `describeReadOp` moved to
  `protocol.ts` so the application layer shares one definition.
- Tests: `FakeClock` and `FakeTui` (scripted keys/confirms/readLines, views
  recorded) added to `fakes.ts`; a new `watch.test.ts` suite covers
  not-a-repo refusal, clean start/quit, own-response and duplicate-hash loop
  prevention, safe-mode confirm/decline, auto-mode automatic reads, batch
  polling, command entry (success + refusal), proposal surfacing without
  overwriting the clipboard, preview, apply (auto + safe-confirmed), cancel,
  sequence apply with post-write verification, mode transitions in the view,
  and clock timestamps. CLI tests cover `watch` parsing, help, and a clean
  `runCli(["watch"])` run. 296 tests pass; typecheck clean.
- Verified the packaged CLI manually on macOS against the real system
  clipboard: safe-mode read round trip (confirm → response copied), auto-mode
  write proposal (surfaced pending → explicit `a` applied → file created +
  `# CTX RESPONSE` copied), own-response loop prevention, `ctx read` batch

## 2026-08-20 — #9 Yolo user mode and notifications

- Added the user-local persisted `yolo` mode and optional desktop
  notifications, completing the fast interactive watcher workflow through the
  same hexagonal boundary.
- New application ports (`src/application/ports.ts`): `UserConfigPort`
  (`readMode`/`writeMode`, storing the watcher mode outside the repository so
  collaborators never inherit a personal automation preference) and
  `NotificationPort` (`notify(title, body)`, optional desktop notices that
  never replace TUI diagnostics). `WatchMode` is now `"safe" | "auto" | "yolo"`,
  and `WatcherView` carries an active `countdown` (`{ label, secondsLeft }`).
  Both new ports are wired into `PlatformPorts`/`main` and the `ctx watch`
  CLI command.
- Infrastructure adapters: `SystemUserConfig` (`src/platform/user-config.ts`,
  JSON at `~/.config/ctx/config.json` on macOS/Linux, `%APPDATA%\ctx\config.json`
  on Windows; missing/unreadable/corrupt storage yields `null` and writes are
  best-effort) and `SystemNotifications` (`src/platform/notifications.ts`,
  `osascript display notification` on macOS, PowerShell WinForms balloon on
  Windows, no-op elsewhere; fire-and-forget, failures never crash the watcher).
- Yolo mode: `m` now cycles safe → auto → yolo → safe and persists each switch
  through `UserConfigPort`; the watcher restores the persisted mode on start
  (defaulting to safe). Valid non-sensitive write proposals enter a cancellable
  three-second countdown rendered one second at a time in the TUI (`runCountdown`),
  then auto-apply through the shared `WriteUseCase.applyParsed` path; any key
  during the countdown cancels the auto-apply and keeps the proposal pending.
  Refused (sensitive without the override, or invalid) proposals are surfaced
  as pending and never auto-apply; with `--allow-sensitive` the explicit
  override lets them validate and count down like any other.
- Notifications fire on request completion (`Request completed`, `Command
  completed`), on pending surfacing (`<Label> pending`), on yolo refusal /
  cancellation, and on every applied/refused/failed write outcome (`<Label>
  applied` / `refused` / `failed`) — always in addition to the TUI event log.
- SystemTui renders the active countdown line (`YOLO — applying <label> in
  Ns — press any key to cancel`); the watch help documents the three modes, the
  countdown, user-local persistence, and the optional notifications.
- Tests: `FakeUserConfig` (in-memory persisted mode) and `FakeNotifications`
  (recorded notices) added to `fakes.ts`; new watch suites cover persisted-mode
  restore on start, full mode-cycle persistence, countdown completion (rendered
  steps `[3, 2, 1]` then applied), countdown cancellation by any key (proposal
  stays pending, nothing written), sensitive-write refusal in yolo without the
  override (surfaced as pending, never auto-applied), sensitive write applied in
  yolo with the explicit override, and notification-port behavior (completion,
  pending, applied, refused) with fakes. 303 tests pass; typecheck clean.
- Verified the packaged CLI manually on macOS in a real PTY against the real
  system clipboard and user config: yolo mode restored from
  `~/.config/ctx/config.json` on start, valid write proposal auto-applied after
  the 3-second countdown (file created + `# CTX RESPONSE` copied), countdown
  cancellation via a key press (file never written, proposal kept pending),

  (never written, refusal surfaced as pending), and the same write applied

## 2026-08-20 — #11 OpenTUI watcher interface

- Migrated the watcher terminal interface to OpenTUI (`@opentui/core`), a
  native Zig-core full-screen terminal UI with Flexbox layout. The migration
  is a platform rendering-adapter change only: every OpenTUI call lives in
  `SystemTui` (`src/platform/tui.ts`) behind the existing `TuiPort` contract,
  and `WatchUseCase` keeps driving the loop through application ports.
- `SystemTui` builds a responsive full-screen Flexbox column — status/mode
  header (safe/auto/yolo color-coded, yolo countdown line), recent activity,
  pending proposed writes, latest copied response, and a persistent
  keyboard-help footer — with confirm rows, the command entry (`InputRenderable`),
  and a full-screen preview overlay. `keyToText` maps OpenTUI `KeyEvent`s to
  the same raw strings the fake TUI scripts, so watcher behaviour stays
  deterministic in the unit suites. OpenTUI loads its native library through
  FFI: supported runtimes are Bun 1.3+ and Node.js 26.4.0 exactly
  (`--experimental-ffi`); elsewhere `open()` throws an actionable prerequisite
  message and `ctx watch` exits non-zero (documented in the CLI help and in
  `docs/smoke-opentui.md`, the macOS/Windows manual smoke path).
- Dedicated prompt action (PRD #11 review gap): the new `i` key copies the
  same startup protocol as `ctx prompt` — the generated protocol plus the
  repository-root AGENTS.md when present (or its reported absence) — through
  the shared `buildClipboardPayload`, without creating or overwriting
  `.ctx.toml`/`.ctxignore` or any other project file. The copied payload's
  hash is recorded for loop prevention, so the watcher never re-executes the
  prompt's own `@ctx` examples on the next poll. The key appears in the TUI
  footer (`[i] prompt`) and in the `watch` help; failures log an event and
  never crash the loop; a notification reports the copy.
- Tests: four new `WatchUseCase` suites with fakes (prompt action copies
